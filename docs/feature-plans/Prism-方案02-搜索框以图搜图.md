# 方案 02：搜索框中的本地以图搜图

日期：2026-10-15。状态：待实施。按用户要求，入口位于现有搜索框右侧，类似提供的 Eagle 截图。

## 1. 要解决的问题与边界

用户拿一张图片，在自己的素材库里找构图、内容或风格接近的图片。**不需要填写 API Key，图片和特征向量在本机处理。** 首次需要准备开源模型；模型和运行时安装后可断网搜索。

这与“重复图片”是两个入口：查重回答是否同一张或几乎相同，以图搜图回答视觉内容是否相关。原有精确查重和感知哈希保留，不把两种分数混成一个“重复率”。本方案不提供全互联网溯源；互联网以图搜图涉及搜索引擎，不包含在本地素材库功能中。

## 2. 直接复用的开源实现

| 层 | 采用项目 | 用法 |
|---|---|---|
| 图像编码 | [mlfoundations/open_clip](https://github.com/mlfoundations/open_clip) | 使用现有模型创建、预处理和 `encode_image()`，不自行训练检索模型 |
| 初始模型 | `ViT-B-32`，候选预训练标识 `openai` | 先做效果/性能样本验证；按发布锁定权重 URL、哈希和许可 |
| 检索索引 | [facebookresearch/faiss](https://github.com/facebookresearch/faiss) | 使用归一化向量和 `IndexFlatIP`，后续有规模证据再换索引 |
| 原始模型来源参考 | [openai/CLIP](https://github.com/openai/CLIP) | 核对模型、预处理与授权；不调用在线 OpenAI API |

OpenCLIP 与 FAISS 代码采用 MIT。具体模型权重与运行时依赖要单独列入发布清单，不能因为库是 MIT 就默认网上所有权重都能随包分发。[OpenCLIP 许可证](https://github.com/mlfoundations/open_clip/blob/main/LICENSE)、[FAISS 许可证](https://github.com/facebookresearch/faiss/blob/main/LICENSE)、[CLIP 许可证](https://github.com/openai/CLIP/blob/main/LICENSE)。

第一阶段使用成熟的 PyTorch/OpenCLIP CPU 路径作为兼容基线，GPU 是可选加速；在独立检索运行时中装依赖，不让主程序启动就导入 PyTorch。现有 ONNX Runtime 不意味着任意 OpenCLIP 模型可以直接运行，第一阶段不自行做模型转换或量化。

Windows 的 FAISS 安装包、Python 3.12 ABI 和打包方式须先做最小验证：确认 CPU 包来源、依赖 DLL、AVX 要求和无开发环境启动。如果选定发行物不支持目标机器，按上游方式构建 CPU 包；不临时写一套替代检索引擎。第一版不承诺 Windows FAISS GPU。

## 3. 唯一主入口：搜索框右侧小图标

示意：

```text
┌────────────────────────────────────────┐
│ 🔍  搜索素材……                  [图片] │
└────────────────────────────────────────┘
```

实现位置是 `prism/search_controller.py` 中真正可见的 `SearchController.input`（`SearchInput`），不是已经隐藏的旧搜索输入框。

- 右侧添加 `QLineEdit` trailing action，使用项目 SVG 图标系统提供“图片+放大镜”图标，跟随深浅主题、悬停及按下状态。与清除按钮分别保留点击区域，至少 28×28 逻辑像素。
- 鼠标提示和无障碍名称统一为“以图搜图”。不能只放一个没有提示的小相机图标。
- 点击图标，紧贴搜索框出现浮层：**选择图片、粘贴图片、拖入图片**。没有剪贴板图片时“粘贴”置灰并说明原因。
- 选中画布的一张图片后，右键提供次入口“查找相似图片”，它填入同一个搜索框状态，调用同一个检索流程。
- 第一版不另外占画布工具栏位置。图片右键是快捷入口，搜索框图标是始终能找到的主入口。

## 4. 从输入到结果的具体交互

### 4.1 选图及查询状态

1. 用户点小图标，选择文件、从系统剪贴板粘贴，或者把一张图片拖到搜索框浮层。
2. 搜索框左侧出现查询图片小缩略图与可关闭的“相似图片”条件；文字过滤仍可输入。不能把文件路径直接当搜索文本。
3. 默认搜索“整个项目”的图片素材。范围选择可改“当前画布/所选文件夹”；标签、评级、类型等已有筛选继续生效。退出图像条件后恢复之前的普通搜索。
4. 立刻出现查询状态反馈：“正在准备模型”“正在分析查询图”“正在搜索”或“正在建立索引，已完成 N/M”。不用一个一直转圈但不说明原因的窗口。
5. 已有部分索引时先在已完成素材中搜索，标明“已检索 N/M 张”；未完成的图片不能被算成没有匹配。索引完成后稳定更新结果，避免每完成一张就重排画布。

### 4.2 结果显示

- 结果在当前搜索结果区域，以可缩放的无限素材画布展示，采用项目已有“最优排列”的布局规则；不是跳出一个白色系统列表窗口。
- 默认取前 200 个，按相似度降序，支持“加载更多”。不能一次给 10 万个结果各建一个 Qt 图元。
- 顶部保留查询图、搜索范围、已索引数、结果数和“退出以图搜图”。初次排序只做一次，缩略图清晰化不改变位置。
- 现有 `SearchCanvas` 目前使用固定信息卡片。实施时保留 `SearchController` 的导航和结果解析能力，给**纯图片结果模式**接入 `AssetCanvas` 虚拟布局；不要直接沿用固定卡片又声称是紧凑素材画布，也不要改坏文档/脑图搜索结果。
- 默认不把余弦值包装成“匹配概率 95%”。显示“相似度高/中/低”或可解释的相似分数，并提示它表示排序相关性。
- 自己作为查询的素材可从结果中隐藏。相同原图出现在多个画布时，可合并成一个结果并显示“N 处”，展开选择具体位置，不删除任何工程素材。

### 4.3 选中、定位、删除和回退

| 操作 | 预期行为 |
|---|---|
| 单击/框选/Ctrl+A | 使用素材画布的选中边框、控制点和选中数量，不只改变内部状态 |
| 双击 | 进入单图预览，支持返回当前相似结果 |
| “在画布中定位” | 按真实画布 ID 打开，左侧高亮切到该画布，仅选中目标素材并居中 |
| 多处出现 | 展示所属画布清单，让用户选一个，不能拿当前页 ID 代替所属 ID |
| 已删除 | 结果即时移除或标记删除，不能定位到另一张图片；撤销删除后恢复 |
| “添加到当前画布” | 是显式复制引用/插入操作，走现有命令和撤销；搜索本身不移动源图 |
| 返回结果 | 还原检索范围、查询图、滚动/缩放位置及选择，避免重新全库推理 |
| 清除查询图 | 释放本次查询数据，恢复原文字搜索；不销毁索引 |

## 5. 接入架构

```text
搜索框图片图标 / 图片右键
        ↓
SearchController（图像查询状态与筛选）
        ↓
检索适配服务（任务 ID、取消、进度、结果 ID）
        ↓ 本机受控子进程
OpenCLIP 编码 → FAISS 查询 → 素材位置列表
        ↓
现有虚拟素材画布 + 现有定位/选择流程
```

计划新增的文件只承担适配职责：`visual_search_service.py` 管理生命周期，`visual_search_worker.py` 调用 OpenCLIP/FAISS，`visual_search_index.py` 管理向量映射和增量事务，`actions/visual_search_workflow.py` 负责选图与菜单衔接。这些是计划名，当前未创建。

结果协议用 `query_id, project_id, generation, asset_id, canvas_id, score`。不跨进程传 Qt 图元、QPixmap 或 Python 对象地址。关闭工程、换工程、改查询时递增 generation，晚到的旧结果直接丢弃。

## 6. 图片从哪里读取，如何保证质量

1. 从项目素材目录和 `source_store` 提取稳定原图来源、格式、内容哈希，不去每个画布重复枚举图元。
2. 不能使用 8px 总览图、受缩放影响的画布截图或假色/曝光临时预览当检索原图。
3. 优先使用经过版本标识、最长边足够的独立分析预览；没有时后台从存储原字节解码。按模型官方预处理输入尺寸处理，屏幕 LOD 的层级选择不影响检索结果。
4. 透明图统一按明确的背景策略合成；EXIF 方向、色彩空间和首帧规则写进预处理版本。第一版只检索静态图像；视频使用封面需作为明确可选范围，不能把整段视频逐帧偷偷入索引。
5. 同一原文件多个素材引用可共用一个内容向量，再通过 occurrence 表找到各个画布。裁剪图是否按裁剪后检索另设选项；默认索引完整原图，查询时可明确选择可见裁剪区域。

## 7. 索引与持久化

索引是**可重建缓存**，原文件始终归原工程管理。放在本机应用缓存目录的 `visual-search/<project_uuid>/<model_fingerprint>/`，不要塞进每次保存必须重写的工程大字段。

| 数据 | 至少保存的字段 |
|---|---|
| 模型清单 | 模型名、权重 SHA256、维度、dtype、归一化方式、预处理版本、应用索引版本 |
| 向量表 | 内容哈希、向量 ID、编码状态、失败原因、最后更新时间 |
| 引用表 | 稳定素材 ID、所属真实画布 ID、内容哈希、删除状态 |
| 构建清单 | 待处理队列、已提交批次、总量、索引 generation |
| FAISS 文件 | 与同批向量映射一致的索引文件及校验信息 |

第一版用归一化 float32 向量和内积索引实现余弦排序，采用 FAISS 原生实现。[FAISS 距离说明](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)。不训练新的距离函数。

512 维 float32 向量的**裸数据计算值**：3,000 张约 5.86 MiB，10,000 张约 19.53 MiB，100,000 张约 195.31 MiB；不包含模型、映射、索引额外开销和解码缓存。模型内存往往比几千张向量更大，不能只展示向量文件大小就说占用很低。

保存索引用临时文件+原子替换和批次清单；只有文件与映射同一 generation 才标记可用。崩溃后跳过已提交内容，续建剩余图片。换模型或预处理必须建立新索引，不能把不同模型的向量混在一起。

## 8. 增量更新与性能策略

| 变化 | 处理方式 |
|---|---|
| 新导入图片 | 加入后台队列，只编码新内容 |
| 重命名/标签/评级变化 | 更新元信息与筛选，不重新编码图片 |
| 画布移动/旋转/缩放 | 只更新归属或定位，不重新编码 |
| 删除 | 引用立即失效，查询结果过滤 tombstone；内容没有活引用后再清理 |
| 撤销删除 | 恢复引用，复用原向量 |
| 修改/替换原图 | 新内容哈希重新编码，旧向量保持到无引用 |
| 重开工程 | 读已保存索引，核对增量，不全库重复计算 |
| 工程另存为 | 明确项目 UUID/派生关系，验证后可复用内容向量，不把旧路径当身份 |

首期 CPU worker 仅 1 个编码任务运行，预取队列不超过 32；初始 CPU batch 8，内存压力下减小。编码线程数有上限，避免后台建库占满 CPU 让画布卡顿。GPU 不足可退回 CPU，不能把同任务错误结果标记为成功。

前 10 万级先测 `IndexFlatIP`。需要扩大时再评审 HNSW/IVF，提供召回率与内存对照；当前几千张素材不先做复杂近似索引。

首轮索引可能花分钟，取决于机器和文件格式；不能承诺用户库“秒建”。模型已经加载、索引已建成后，目标是 1 万张的查询图编码+检索+首屏呈现 p95 不超过 1 秒，GPU 目标 500 ms。另测冷启动、模型载入、首轮建库、增量 100 张和取消耗时。这些都是待实测目标。

## 9. 实施与验收表

| 阶段 | 交付 | 验收 |
|---|---|---|
| V1 上游运行时 | OpenCLIP CPU 编码、FAISS Windows CPU 查询、锁定权重 | 无开发环境机器离线运行；依赖及模型授权清楚 |
| V2 索引适配 | 内容哈希、向量与引用映射、增量事务 | 崩溃续建；重开不全量推理；删图/撤销一致 |
| V3 搜索框入口 | 右侧图标、浮层、查询缩略图、取消状态 | 位置与用户截图一致；拖入不误导入画布；中文输入法正常 |
| V4 画布与定位 | 虚拟图片结果、最优排列、真实画布定位 | 点击后左侧高亮、选中控制点与居中均正确 |
| V5 性能与发布 | CPU/GPU 基线、离线包、诊断和上限 | 建库期间平移缩放不中断；3千/1万/10万测内存和响应 |

效果验收样本至少包含建筑、人物、道具、拼图、透明图、同图缩放、裁剪及颜色接近但内容不同的图片。由用户选至少 20 张参考图，记录前 10 个结果是否有实际用途；不能只凭“找到了自己”验收语义检索质量。

故障验收：模型未装、权重损坏、原图缺失、索引一半断电、CPU-only、显存不足、删除结果、删除后撤销、快速换查询、查询时换工程、退出应用、不同路径同名素材。每项有明确提示且不破坏工程。

日志事件：`visual_search.model_load / index_batch / query_encode / query_search / results_publish / cancel`；记录分阶段时长、batch、设备、素材数量和索引版本。不要保存用户查询图片到操作日志，也不上传图片到任何在线 API。
