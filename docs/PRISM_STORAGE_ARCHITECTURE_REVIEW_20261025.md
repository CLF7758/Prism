# Prism 存储与十万素材架构评审、旧工程兼容及迁移方案

日期：2026-10-25  
性质：结合当前源码与已有取证的设计评审；不是已完成的开发，也不是迁移工具使用说明。

## 0. 评审立场与结论

用户描述的“大文件、保存慢、计数滞后、十万素材卡顿、希望更小且不损坏原件”是问题输入，不等于指定技术方案。专业评审不先决定分区、换数据库、提高压缩等级，也不会承诺某种架构让所有问题消失。

本方案把事实、推断、推荐与待验证项分开。设计目标和验收门槛是本次提出的工程建议，应在实施前冻结；文中的建议参数不是已有产品保证。

**推荐的方向：先把“工程元数据、不可变原件、可重建派生物、界面工作集”分成独立边界，再引入可选分离式工作工程；保留旧 `.prism` 后端，迁移只生成新副本。**

具体判断：

1. 当前 `.prism` 是 SQLite 数据库，不是只能整体解压的 ZIP。文件大不意味着读取、保存必须全量处理；首先修正读取、保存、缓存失效和驻留边界。
2. 元数据持续变化，原件通常不变，预览可以重建。把它们绑定在同一个文件修订上，会使小改动被放大。这个耦合比“只有一个文件”更值得先处理。
3. 分离式工作目录适合作为大库候选；在独立样本证明收益之前，不能强制所有用户迁移。
4. 自包含单文件仍有价值，应保留为旧格式和便携交付选项。工作格式与分享格式不必相同。
5. 压缩优先级为：字节相同的原件去重 → 不携带可重建缓存 → 减少元数据与版本冗余 → 按数据类型选择可逆压缩。最高压缩等级不适合作为日常保存策略。
6. 十万级顺畅的关键是有索引的查询、紧凑结果、可复用布局和有界界面对象；换成一万个小文件，也不能修复全量代理与 GC 长尾。

**本次仅交付方案和研究证据。没有更改产品代码、依赖或现有文件格式；没有打开、转换、压缩、导出用户工程。**

### 后续深层验证补充（同日）

已在隔离环境运行对象库、合成旧schema迁移/回转、取消续传、中断协议、十万索引与可逆压缩实验。核心方向可进入开发，但发现默认DOS读取会在源目录创建WAL/SHM，不能直接作为严格只读后端；普通read也不自动校验完整内容哈希。静止索引复制到私有缓存的窄适配已作小原型，活动索引、pack pin、ACL只读和正式媒体接线仍是开发闸门。

旧结构原型验证了10000实例、10张表与未知普通字段的完整回转，但未在任意旧程序二进制或真实用户大工程上验收。首个逐项检查点原型90秒超时，保留失败后改批次与重复内容处理，未扩大限时。压缩样本说明文本可受益，而PNG/JPEG不能承诺继续缩小。

因此下面的“推荐候选”不等于直接采用默认配置；实施以新文档`docs/PRISM_STORAGE_DEVELOPMENT_PLAN_20261025.md`的16步和5个闸门为准。实证范围与失败记录见`artifacts/storage-feasibility-20261025/REPORT.md`。

## 1. 专家会先看什么，而不是先照现有设计改

### 1.1 原始材料与问题

| 原始材料 | 专家要回答的问题 | 不能替代它的材料 |
|---|---|---|
| 实际数据库 schema、表数量、页大小、空闲页、BLOB 长度分布 | 文件中到底是原件、重复内容、缓存还是空闲页占空间？ | 文件总大小截图 |
| 原件类型、尺寸、字节哈希、重复分布 | 十万素材到底有十万个独立原件，还是大量实例共享少数原件？ | 素材行数 |
| 一次打开、查询、缩放、编辑、保存的请求链 | 用户动作引发多少 SQL、原件读取、评估、代理、布局、绘制？ | 单个总耗时 |
| 操作系统进程 I/O 与应用读写计数 | 真正读写了多少；有多少是缓存命中？ | 用55GB推断本次读了55GB |
| 对象持有图、GC、Qt/图像原生内存 | 慢在磁盘、解码、安装还是存活对象遍历？ | RSS 一个数字 |
| 未加载行、未知JSON字段、附件、跨画布关系 | 保存或迁移是否完整保留数据？ | 当前画面看起来正常 |
| 中断、满盘、锁冲突、退出和恢复证据 | 成功提示对应哪个真实提交点？ | 单次正常退出 |
| 用户常用动作与工程分布 | 需要优化哪些主要工作负载？ | 只以压力夹具决定所有产品行为 |

先在专用副本做分布统计和实验。对大原件全量哈希是有成本的维护工作，放在后台、可取消；不能变成每次打开的前置步骤。

### 1.2 先分清三个“数量”

- **素材实例数**：画布上可独立打标签、移动、删除的条目数。
- **独立内容数**：按完整原件字节身份去重后的数量。
- **当前工作集**：视口、预取邻域和用户正在操作的对象。

它们可能相差几个数量级。实例数决定查询和索引规模；内容数决定原件空间；工作集决定解码和界面驻留。任何一项都不能用另外一项代替。

### 1.3 先区分两类“包体”

本方案主要讨论工程体积，不讨论立即给程序重新打包：

- **程序安装体积**：Qt、WebEngine、解码器、运行时、模型等。压缩工程不会减少这些依赖。
- **用户工程体积**：原件、附件、正文、元数据、预览、SQLite空闲页和备份。需要单独拆账。

增加开源依赖也会增加安装和维护成本，必须把传递依赖及Windows二进制轮子纳入评估。

最近PID56200热点修补仅处理行号调度/绘制判断和保存片段日志溢出，不能据此宣称存储、全库查询和GC已经闭环。

## 3. 架构目标：专家会先约定的正确性

以下是推荐采用的验收契约，而不是从用户的每个担忧机械推导一个功能。

### 3.1 数据语义

1. 原件以字节对象保存。导出原件应与入库时字节相同，涵盖ICC、EXIF、动画帧、音轨及未知附加数据，而不只是像素看起来一样。
2. 裁切、旋转、材质参数、标签和布局是实例元数据，不覆写原件。可以另设明确命名的“导出处理结果”。
3. 相同字节可以去重，实例不能合并。两张看起来相同但字节不同的图，不自动视为同一原件。
4. 缺失、空内容、未加载、损坏、权限失败是不同状态。不可用时明确报错，不能用空文件、预览或默认值冒充成功。
5. 老文件中若早已只剩重编码图片，迁移只能证明“迁移前后现存字节相同”；不能补造导入前的原件。

### 3.2 版本与提交

- 保存提交的单位是捕获修订R；捕获之后的新编辑仍为dirty，不能随旧回执清除。
- 磁盘已提交但GUI未确认，与未提交分别处理；重复回执必须幂等。
- 文件mtime用于外部变更预警，不作为所有素材和预览的统一语义修订。
- 更新正文或标签，不应导致未变原件重新哈希、重新编码或重建全部预览。
- 缓存全删后工程仍完整可打开；缓存不是权威数据。

### 3.3 界面与工作集

- 打开先得到工程头、首张有效画布和可见区域，不以全库计数、原件扫描或迁移为前置。
- 全库计数、结果数、当前画布数、可见数、绘制数、选中数分口径；未知显示准备中，不能显示假0。
- 查询缓存命中不等于安装/布局成本为0；所有阶段分别计量。
- 远景派生预览不改变原件和最终清晰度；放大后应完成全视口清晰恢复，不能永久只保留鼠标附近。

## 4. 候选架构与选择

| 方案 | 优点 | 代价与局限 | 本次结论 |
|---|---|---|---|
| A 继续单文件SQLite | 便携、事务成熟、旧版适配成本低 | 原件与元数据生命周期耦合，另存大库昂贵 | 保留并优化，不淘汰 |
| B SQLite元数据＋分目录原件 | 容易检查、独立读取、备份粒度小 | NTFS小文件/杀毒/目录遍历开销，复制碎文件慢 | 对照候选，不能只测顺序读取 |
| C SQLite元数据＋内容寻址对象库，loose与pack并存 | 去重、批量读取、限制目录项、原件与元数据分离 | 两套持久化协调、回收与pack维护更复杂 | 大库工作格式推荐候选 |
| D 每张画布一个数据库 | 单页文件看似小 | 全库标签/搜索/跨页移动/共享原件变复杂 | 不作为主方案 |
| E 整个工程一个高压缩solid包 | 某些数据压缩更充分 | 随机读、更新、损坏恢复与首屏差 | 仅离线归档候选，不作工作格式 |

**推荐落地顺序：先完成A与C共享的来源/修订/事务边界，再做C的隔离原型与对照；收益、安全、Windows媒体接线均通过后，C作为用户可选项。**

SQLite本身支持按需读取、局部更新和作为应用文件格式；不能把当前全量处理归因于它必须整库读写。[SQLite应用文件格式](https://www.sqlite.org/aff_short.html)

## 5. 推荐工作格式与产品入口

### 5.1 目录结构（建议命名，实施前冻结）

```text
我的工程/
  我的工程.prismproj        小型入口manifest；含magic/格式/能力/相对路径
  metadata.sqlite          工程权威元数据、对象引用、修订、保存日志
  objects/                 第三方对象库自管理；其内部文件布局不由UI依赖
  recovery/                迁移检查点、操作恢复资料
  README.txt               搬迁与恢复提示，无用户敏感日志

本机缓存目录（默认不随工程移动）/
  previews/<storage-id>/   可重建分级预览
  layouts/<storage-id>/    可重建查询/几何结果
```

预览可提供单独“携带预热缓存”选项，但不能把它计入原件数量或权威内容。不要同时强制保留一套巨型旧`.prism`作为新工程的运行依赖。

### 5.2 入口与身份

- `.prism`：继续表示旧SQLite自包含工程，不悄悄变成指向目录的快捷文件。
- `.prismproj`：新工作工程入口；只能指向工程根内受控相对路径。限制manifest大小、禁止绝对路径/`..`/符号链接逃逸，验证真实规范路径。
- `.prismbundle`：可选的新格式便携包，导入到目录后工作，不直接在压缩包内编辑。
- 入口manifest只记录格式能力，不在每次保存时与数据库争当两份权威状态。工程修订以数据库为准。
- 迁移保留旧工程的业务`project_id`和实体ID；增加独立`storage_instance_id`，另有每次打开的`open_epoch`。工程副本、原件身份、会话身份分开，防止原件/计数/异步回调串库。
- 新格式必须声明`format_version`、`min_reader_version`、`required_features`、`object_backend`和`codec_set`；未知必需能力拒绝打开写入。可理解的只读子集要明确标注，不能写回。
- 重定位目录不改变内容身份；绝对路径只作为外部链接提示，不成为内部原件的唯一来源。

### 5.3 新工程元数据

首版继续SQLite，保留现有items、页面、材质、资源树等业务语义。建议新增下列结构，最终SQL要在原型和迁移测试后冻结：

| 结构 | 作用 |
|---|---|
| project_state | 业务ID、storage ID、schema、单调提交修订、能力 |
| objects | 完整原件SHA256、长度、媒体类型提示、存储后端定位、校验状态 |
| object_refs | item/attachment/material等实体到原件的关系，含role/ordinal |
| object_variants | 同一原件的物理编码或位置；原件哈希与存储字节哈希分开 |
| entity_revisions | 实体元数据、正文、几何等相关修订 |
| save_operations | operation_id、捕获修订、实际提交修订及状态 |
| change_log/outbox | 提交内记录的变更集合/领域修订，供目录和UI幂等消费 |

不要把正文按整页巨型JSON随页面清单读取。新格式把页面头与body分开；老后端保留信封读取器。正文可按页延迟，但未加载状态必须可无损保存/导出。

标签关系和分类关系需要可索引的正规化投影；JSON仍保留原字段和扩展，不以投影覆盖未知数据。全库目录可以渐进重建，不能成为打开首屏的必要条件。

## 6. GitHub已有实现：复用什么，不能假装复用了什么

研究采用官方仓库与官方文档。环境没有`gh`，GitHub API又返回限流，改用GitHub网页、raw发布标签和PyPI JSON核验；未绕过账号权限。下载内容仅放研究目录，未导入/运行第三方源码，未安装进产品环境。

### 6.1 对象库：disk-objectstore 1.5.0，优先适配候选

[GitHub仓库](https://github.com/aiidateam/disk-objectstore) · [v1.5.0源码](https://github.com/aiidateam/disk-objectstore/tree/v1.5.0) · [MIT许可证](https://github.com/aiidateam/disk-objectstore/blob/v1.5.0/LICENSE.txt)

它提供基于内容哈希的对象访问、流式导入读取、散对象与pack、索引和校验等现成能力。本次读取的CI声明包含Windows和Python3.12；这是候选依据，不等于Prism集成已通过。依赖包含SQLAlchemy和click，不能说“零新增依赖”。[项目配置与CI](https://github.com/aiidateam/disk-objectstore/tree/v1.5.0/.github/workflows)

**复用边界：** 通过薄适配层调用公开API，不复制其pack实现重写一套，不让业务查询直接操作它的内部数据库。

| 公开能力 | Prism用法 | 限制 |
|---|---|---|
| `add_streamed_object` | 临时/增量原件入库并由库计算内容身份 | 不先把大原件读成一个bytes |
| `get_object_stream` | 解码、导出、校验 | 仅保证read，不保证seek；视频等接物化租约 |
| 批量流读取 | 后台迁移/批量导出 | 返回顺序可能按存储优化，必须按ID匹配，不按zip位置匹配 |
| pack/validate | 降低小文件数量与维护校验 | 单pack写者，维护不能与任意清理并跑 |

流式和批量读取的这些约束来自其公开接口；不能调用无参数`read()`把大对象一次装入内存。[流式与批量API](https://disk-objectstore.readthedocs.io/en/latest/pages/advanced_usage.html)

**不能直接接受的默认值：** pack大小是目标值，不是硬上限；单个大对象可使它超出目标。日常不自动全量repack。视频/GLB优先不做额外压缩，随机读取或物化实测后决定。库的备份工具不能直接当Windows工程备份方案。

loose打包后不立即删除被打开的对象；Windows文件句柄和清理行为要走现有lease/drain协议。pack维护与清理的并发限制须遵守官方说明。[打包与清理](https://disk-objectstore.readthedocs.io/en/latest/pages/packing.html)

**引入闸门：** 正常读取可只读使用、打开不创建维护文件、Windows中文/长路径、无seek媒体、满盘/中断、两库提交顺序、pack维护与租约、恢复校验全部通过，才允许进入正式路径。若失败，B方案可作临时原型，不为赶进度fork一个复杂pack引擎。

### 6.2 强压缩：python-zstandard，放在独立可逆编码层

[Python绑定](https://github.com/indygreg/python-zstandard) · [算法实现](https://github.com/facebook/zstd)

本次PyPI核对`zstandard=0.25.0`有CPython3.12 Windows x64 wheel；项目声明BSD-3-Clause。Zstd提供可调压缩等级和字典能力，但官方通用语料成绩不能当Prism图片库收益。[算法说明](https://facebook.github.io/zstd/)

**重要：disk-objectstore 1.5.0默认编码为zlib，不能直接传`zstd`就假装兼容。** 首版工作对象库使用其原生能力；Zstd先用于`.prismbundle`逐对象可逆包装及元数据归档。若以后需要工作库Zstd，要单独评审`object_variants`编码适配，不修改库内部格式冒充原生支持。

### 6.3 工程锁：优先已有Qt，再评估portalocker

第一版单工程单写者，优先`QLockFile`与SQLite事务。若独立迁移CLI需要跨平台共享锁，候选为[portalocker](https://github.com/wolph/portalocker)，许可证BSD-3-Clause；必须使用同一锁协议，不能Qt端与CLI各锁各的。文件锁只协调遵守协议的进程，不能据此宣称能阻止任意旧程序或云盘写入。

### 6.4 不选作新核心的东西

- `python-atomicwrites`已归档且说明不再维护，不为了一个`replace`再引入它；用标准库同卷临时文件、校验、替换及故障恢复。[仓库维护声明](https://github.com/untitaker/python-atomicwrites)
- 不换成服务器数据库来解决本地画布问题；不引入分布式对象服务。
- 不把整个工程作为一个solid压缩流，不用最高等级压缩阻挡交互保存。
- 不引入图片有损转码、感知去重或“看起来一样”的替代原件。

### 6.5 依赖固定与许可证交付

研究目录记录下载文件SHA256；DOS使用发布标签源码，main抓取仅作背景对照。正式引入前固定版本和所有传递依赖的wheel哈希，保存许可证、NOTICE与来源清单。MIT/BSD项目保留相应声明；不得仅凭仓库名字或星数判断可用。

## 7. 体积与压缩：如何小，而不牺牲原件

### 7.1 首先算清楚账

设实例原件总字节为B，按完整字节去重后为U，额外可逆压缩后的原件为C，权威元数据为M，索引为I，携带预览为P：

```text
工作工程≈对象存储开销+U或其原生可逆编码+M+I
便携工程≈清单开销+C+可逆压缩的M+可选P
去重收益=B-U；额外压缩收益=U-C
```

另计文件系统簇、SQLite空闲页、备份、临时副本、物化和本机缓存。传输大小、逻辑字节、物理占用、峰值临时空间四列分别报。

如果55GB主要是独立且已压缩的JPEG/视频，可逆压缩未必明显缩小；如果同一原件被存了许多次，字节去重可能更有效。这两种情况要实测，不能依据行数猜比例。

### 7.2 压缩决策表

| 数据 | 日常工作策略 | 离线紧凑导出策略 |
|---|---|---|
| JPEG/PNG/WebP/AVIF、MP4等已压缩原件 | 原字节，不重编码；通常不二次压缩 | 可抽样评估，无收益就STORE；不能强行转格式 |
| BMP/TGA、可压缩二进制、未压缩纹理 | 保原字节；库原生可逆压缩需收益/解码测试 | Zstd独立帧，解压还原同一字节 |
| HTML/JSON/脑图正文 | 按页访问；用于查询的字段保持可索引 | Zstd或Deflate，按页/有限块而非整库solid |
| DOCX/ZIP等复合原件 | 作为不透明对象保留 | 不拆开重组来声称字节无损 |
| 字节相同的原件 | 共享内容对象，实例引用独立 | 包中只存一份对象 |
| 缩略图与组合预览 | 本机有界缓存、可重建 | 默认不携带；可选携带，不替代原件 |
| 字典 | 首版不训练 | 二期仅限同类小文本；字典随包携带并校验 |

压缩收益试验建议比较STORE、zlib、Zstd 3/6/9、LZMA；高等级Zstd只作离线候选。用真实格式分布、总耗时、压缩比、解压P95、内存和随机访问代价选择，不按最高比率单项获胜。

样本检测用于决定是否尝试压缩，不能作为完整原件身份或完整校验。未知大小内容必须流式，限制输出长度和解压窗口；不能信任文件宣称的长度。Zstd上下文按逻辑任务独立使用，不能多线程共享同一实例。[压缩接口](https://python-zstandard.readthedocs.io/en/latest/compressor.html) · [解压限制](https://python-zstandard.readthedocs.io/en/latest/decompressor.html)

### 7.3 `.prismbundle`建议封装

首版可复用Python3.12的ZIP64作为目录容器：manifest、冻结元数据和逐对象entry；Zstd对象先独立编码，再以ZIP_STORED装入，避免双重压缩。ZIP64支持超过4GiB，但Python3.12的zipfile不原生提供ZIP_ZSTANDARD，也不支持多磁盘ZIP，不能直接用不存在的能力。[Python3.12 zipfile](https://docs.python.org/3.12/library/zipfile.html)

每个entry记录原件SHA256/长度、存储字节SHA256/长度、codec与版本、关联关系；导入按原件哈希校验，扩展名只是展示。不要对整个ZIP再套一个必须全解才能访问的压缩层。

若确有单文件大小限制，后续提供运输分卷及manifest重组；这不等于工作库分区。DOS的pack target也不保证每文件小于4GB，FAT32等硬限制要明确拒绝或选择另一交付方式，不能写到一半才报成功。

### 7.4 “导出什么”的产品语义

- **导出原件**：导出对象原字节；不经过QImage保存，不丢EXIF/ICC/帧/音轨。
- **导出处理结果**：用户明确选择后的裁切/合成/文档转换，生成新作品，不称其为原件。
- **导出整个工程**：带完整实例、关系、正文、全局元数据及所有必需原件；预览可省，不允许正文省略。

批量原件同名时输出名称需无覆盖冲突，附原实体ID与哈希映射。原文件名、目录语义、来源信息留在元数据，哈希文件名不代替它们。

## 8. 现有性能瓶颈必须如何一起处理

| 现有问题 | 根本边界 | 设计动作 | 不成立的捷径 |
|---|---|---|---|
| 首屏受目录/计数拖累 | 打开阶段耦合 | 头/首画布先完成，目录后台；发布带open epoch | 拆成多文件后仍等全库 |
| 未标签/未分类/复杂筛选全量评估 | 查询与索引 | 可表达条件下推、EXPLAIN验证、dirty覆盖集正确合并 | 只缓存原图 |
| 切换回来重复安装 | 结果/几何生命周期 | 复用紧凑ID顺序和几何token，实体变化才局部更新 | 只报告read_rows=0 |
| 代理规模和gen2长尾 | GUI对象图 | 可见/邻域物化；结果存ID/紧凑列，明确持有者总预算 | 关闭GC或无限提高缓存 |
| 保存准备扫描/深拷贝 | 变更模型 | 显式实体patch和冻结修订；未知改动拒绝快路径 | 换格式但仍遍历全场景 |
| 保存后预览/目录全失效 | 身份过粗 | 内容身份、领域修订、事务变更回执 | 忽略所有mtime变化 |
| 冷原图读与解码长尾 | I/O/codec调度 | 小批预取、后台流、焦点优先且公平遍历全视口 | 全部解码后才显示 |
| 材质折叠抖动 | Qt布局 | 稳定宽度/沟槽、预览不参与尺寸协商、原生逐帧验证 | 更换存储 |
| 原生退出访问冲突 | 资源生命周期 | 停接单→撤消/完成→回调隔离→drain→销毁QObject | 以目录格式推断已解决 |

查询、计数、几何共享修订协议，但缓存键不应完全相同。几何还依赖结果顺序、尺寸/裁切/变换、pack算法、视口/DPR；相同筛选不代表相同几何。

结果ID紧凑存储，重代理、解码像素、Qt纹理、组合预览分别预算。已估计字节与实际计量分列；缓存预算不是RSS上限，GPU未知不能写0。禁止为了热切换全命中而无限驻留十万个对象。

### 8.1 查询如何避免“只是把大文件变成很多文件”

新格式建议以实体ID作为连接点，维护画布、类型、回收状态、标签关系、分类关系及确定排序列的索引。标签无/分类无优先用有索引的反连接或等价查询；先在真实分布上用EXPLAIN QUERY PLAN确认，不能只看到WHERE就声称没有扫描。复杂AND/OR/NOT和页面/材质口径要做集合真值对照。

排序必须稳定，以排序值加唯一ID作为keyset续页键；同时处理NULL、中文排序规则和相同值。不能在每一页重复OFFSET跳过前面所有行，也不能在dirty覆盖后打乱续页边界。

未提交编辑作为显式overlay：从数据库候选中排除被修改/删除ID，再把重新匹配且按相同排序语义排序的dirty项合并。改标签使某项跨入/跨出未标签集合时，结果与计数必须一致。数据源快照、查询generation、overlay修订、分页游标绑定，任一不兼容变化均使旧回调失效。

QueryKey负责结果匹配；ResultPublication负责“谁发布哪个修订”；GeometryKey再加结果顺序与几何输入。无需每次切换重新计算全库哈希，身份摘要由受控修订增量维护。复用一串ID仍可能O(N)复制，因此消费者要支持不透明结果句柄与分片安装，不能把tuple换成list就宣布安装成本消失。

### 8.2 一次专业设计应设置的成本上界

- 一次普通标签保存的成本随变更数和索引更新增长，不随原件总字节增长。
- 一次视口恢复的重对象和像素成本随可见区域/邻域增长；全库紧凑索引可以增长，但不能为每行都保留Qt卡片及多套Python容器。
- 一次原件导出的最低工作量就是所导出原件字节，不能把它优化成只写预览。
- 一次首次完整迁移和完整校验需要遍历全部权威内容，这个O(B)不能伪装成O(1)；优化的是流式、恢复点、去重写入和不阻塞UI。
- 全新复杂筛选可能仍有不可避免的评估；应先下推可用索引、复用已证实结果，再明确展示剩余工作，不提前缓存所有查询组合。

这些是架构应争取的复杂度边界，不是未经实验的绝对毫秒承诺。

## 9. 存储适配：改哪些边界，不把if目录散满全项目

建议新增三个薄模块，名称可在实施前统一：

1. `prism/storage/project_backend.py`：内容探测、版本门禁、LegacySQLiteBackend与DirectoryBackend路由。
2. `prism/storage/object_repository.py`：对象入库/流/长度/身份/物化/校验；DOS适配只在这里。
3. `prism/storage/migration.py`：检查、计划、复制、校验、发布、恢复；独立于GUI场景。

不要把整个现有IO层一次推倒。先让旧后端实现接口并跑原回归，再加新后端。对象引用由`(filename,item_id)`等隐式元组逐步收敛为明确`SourceRef`，旧元组由适配器转换，不允许有的模块改了、有的仍把目录当SQLite连接。

建议接口表达能力而非巨型通用类：

```text
ProjectBackend: probe/open_snapshot/read_headers/read_page_body/
                query_ids/apply_changes/export_legacy/close
ObjectRepository: put_stream/open_stream/stat/verify/materialize/close
SourceRef: storage_instance_id, object_id, content_revision, role
SaveReceipt: operation_id, captured_revision, committed_revision,
             changed_entities, complete, durable_state
```

`changed_entities=unknown`不能同时作为完整增量凭证。清晰恢复或计量异常不得阻止已完成像素安装。每线程只用自己拥有的数据库连接/对象库会话，关闭协议沿用stop/drain，不把一个可变SQLAlchemy session共享给所有解码线程。

## 10. 旧用户与旧软件的兼容，必须分开承诺

| 场景 | 应提供的行为 |
|---|---|
| 新版程序打开现存`.prism` | 继续直接打开；不强制拆分，不在首开偷偷迁移大库 |
| 旧版程序打开未改变的旧`.prism` | 保持既有兼容范围；不能承诺旧程序理解它发布之后的新业务字段 |
| 新版保存旧`.prism` | 继续旧后端，未知字段/未加载行不能丢；能力不足明确拒写 |
| 新版打开新`.prismproj` | 经版本/能力门禁后按新后端工作 |
| 旧版打开新`.prismproj`或`.prismbundle` | 无法凭空支持；应使用新版，或由新版生成兼容`.prism` |
| 新目录导出兼容`.prism` | 所有引用重新内嵌，核对原件与关系，声明目标程序/格式版本 |
| 新功能无法由目标旧版表达 | 列明不兼容项；拒绝称“完整兼容”，不能静默删除 |

“老用户能正常打开”优先指老工程在新程序正常打开；“老软件能打开新格式”是另一项，需要显式兼容导出。不能为了假兼容把新目录藏在`.prism`后面，让旧程序误写。

UI建议：保留“打开”“保存”，新增“转换工程存储…”和“导出兼容工程…”。转换前展示源路径、目标目录、空间估算和原件/链接清单；默认保留源文件。不要在保存按钮里混入全库压缩与整理。

## 11. 将旧大文件拆开：可取消、可恢复、原件不动

### 11.1 拆分的含义

拆分是**逻辑读取旧SQLite → 新元数据与对象库 → 完整核验 → 发布新工程**。不是按二进制偏移把55GB文件切几段；也不是把十万画布分别存成十万个数据库。

第一版离线转换：要求源工程在本应用中无未保存编辑、无保存/导入任务；不支持一边编辑一边迁移。不能关闭用户窗口；提示用户选择合适时机或专用已保存副本。

### 11.2 状态机

```text
DISCOVER → PREFLIGHT → COPY_METADATA → COPY_OBJECTS
         → VERIFY → FINALIZE → PUBLISH → COMPLETE
任何阶段 → PAUSED / CANCELLED / FAILED（保留原文件）
```

目标先在目标磁盘的同父目录`.partial-<operation_id>`里创建，只有最终发布才使用正式入口。用户看到“已复制”和“已验证”是不同进度。

### 11.3 M0：预检

1. 内容探测和schema/能力检查，不只看扩展名；禁止自动创建一个不存在的源数据库。
2. 只读连接，不执行源内未知触发器或扩展；枚举表/列/索引、语义引用、sqlar和attachments长度、空正文和链接情况。
3. 记录源文件身份、schema、项目ID及活动journal/WAL。活动WAL是数据的一部分，不能只复制主文件，也不能随意使用`immutable=1`。
4. 检查源/目标是否同一文件或目录别名、卷能力、目标权限、路径长度、空间；拒绝覆盖既有目标。
5. SQLite统计只说明逻辑内容和页，不等于实际I/O。空间估算按不去重、不压缩的保守上界，另加元数据、临时校验和库维护余量；不要承诺固定倍数。
6. 对更旧schema先判断只读适配能力。没有适配器时，明确要求先生成升级副本并显示额外空间；不能复制55GB后才发现磁盘不足，也不在原件上跑升级。

### 11.4 M1：一致来源

首版选择明确的维护窗口：源不得有外部写者，转换期间持有已验证的只读快照和必要数据库读锁，保证所有BLOB及metadata来自同一修订。回滚日志与WAL要分别测试：长读取可能阻止写入或使WAL增长，不能笼统称“完全不影响编辑”。

若无法保证独占维护条件，使用SQLite Backup API生成一致源副本再转换，并明确它需要整库额外空间与I/O；不默认偷偷使用。用户不接受维护窗口也没有空间时，允许不转换，旧格式仍可用。[SQLite Backup API](https://www.sqlite.org/backup.html)

stat前后相同不能证明内容相同。续传绑定源快照/逻辑修订与检查点；跨进程重启后若源改变或无法证明未变，旧检查点不得拼入新快照。可以逐项重新验证并复用已校验对象，但要重新建立完整一致清单。

### 11.5 M2：复制元数据

- 复制全部实体，保持ID、顺序、画布映射、标签/分类层次、材质绑定、注释、正文、节点、回收站与未知JSON字段。
- 新DB直接构建元数据，不采用“完整backup55GB→删BLOB→再VACUUM”作为默认拆分流程；后者先承担大副本又产生重写峰值。
- 采用分页/keyset有界复制，不先构造十万个Qt对象，不通过scene.items()枚举完整工程。
- `workspace_pages`未加载正文按权威源读取；空、缺失、未加载分开。页面头与body分拆时保留原信封可回溯映射。
- 未知列保留类型和值；未知普通表需要schema与行级保真方案。未知虚表、触发器、扩展或无法解释的引用不能悄悄略过：预检阻挡并列出原因，必要时保留独立兼容载荷，但没有可验证回放就不能宣称完整转换。
- 源文件当前是否“坏”与“不支持”分别反馈，不能自动删表修复后继续报成功。

### 11.6 M3：流式复制原件与附件

按`sqlar`和`attachments`的真实行枚举，读取其rowid和长度，再用blobopen/受控分块流复制。不能`SELECT data FROM sqlar`整表fetchall，不能经图像解码再保存。

当前Prism的SQLAR扩展含item_id；旧版本数据编码必须由旧后端判定，不能只因为表名相同就盲目zlib解压。标准SQLAR允许压缩/未压缩两种内容；归档载荷哈希与用户原件哈希需分开记录。[SQLAR格式](https://sqlite.org/sqlar.html)

逐对象流程：读取权威内容 → 完整SHA256与字节计数 → 第三方对象库流式写入 → 对照库返回身份 → 回读解码后的原字节哈希 → 记录映射与已验证检查点。发现同字节原件复用对象；保留每个原文件名和实例关系。

旧工程里可有不再被活动画布引用的原件或未知关系，第一版转换保守携带，不擅自当垃圾删掉。纯外部链接应保持原来的链接语义并提示；若用户选择“自包含转换”，缺失/变动的外链必须阻止完整成功，不能悄悄导出预览。

检查点按完成对象记录，不尝试恢复到一半的压缩帧。半成品可丢弃重做，不把所有已完成对象重新复制。检查点自己也要事务化、绑定源身份和目标storage ID。

### 11.7 M4：验证与发布

必须验证：

- SQLite完整性/外键及领域引用；实体ID集合、行数、几何值、标签关系和正文语义对照。
- 每个原件/附件的长度和完整SHA256；所有必需引用可解析，未知数据保留范围有清单。
- 从新后端原件导出到专用目录后哈希一致；取消旧源路径访问后，新工程仍能重开、解码、播放和导出。
- 元数据和对象索引均关闭/持久化后发布；只有正式入口存在且最终校验通过才标COMPLETE。

同卷rename/replace能降低半成品可见风险，但Windows打开句柄、设备缓存和断电行为不能靠一个API名证明。发布记录、目录入口、对象索引与DB均纳入故障注入。原子可见与断电持久是两个验收维度。

迁移成功后仍不自动删除源文件。展示原/新逻辑体积、实际占用、原件校验数量、去重与压缩各自收益、未支持项和源路径。用户自行决定清理，应用不代替删除。

## 12. 新后端的保存、回收、备份与退出

### 12.1 跨数据库不是一笔魔法事务

工程metadata与DOS对象索引不能假定跨库原子提交。推荐顺序：

1. 写入新对象并持久化，得到已验证可读身份。
2. 单一metadata事务提交对象引用、实体patch、修订和outbox。
3. 事务提交后确认保存；GUI只确认捕获修订，后续编辑保留dirty。
4. 崩溃在1与2之间最多产生未引用对象，后台可回收；不能先提交引用再等待对象落盘。

删除反向处理：先提交逻辑移除/墓碑；等待撤销历史、备份pin、导出pin、物化租约与读者都释放，再做维护回收。参考计数可以作加速信息，回收前以可达性校验为准；不能因一个损坏计数永久删除原件。

### 12.2 事务与WAL

本地工作metadata可评估WAL，单writer、短事务、每线程独立连接；后台checkpoint可观察，不在鼠标事件中强制大checkpoint。只读/网络共享/同步盘另立支持策略，首版不宣称可在任意网盘路径多机并写。[WAL约束](https://www.sqlite.org/wal.html)

整个目录备份不等于依次复制几个文件。先冻结metadata快照和对象可达集合、pin这些对象，再复制校验；期间不回收它们。对象库维护与备份要通过同一维护协调器。

### 12.3 维护与压缩

pack/repack/去重扫描/全库校验是低优先级、可暂停的维护任务，不能与原生性能测量混跑后把结果当单独负载。首版禁止自动全库repack与自动大VACUUM。

SQLite删除BLOB后空间可能留在freelist，并不会立即变成操作系统空闲空间；VACUUM是重建，不能每次保存都运行。[VACUUM说明](https://sqlite.org/lang_vacuum.html)

### 12.4 退出

复用已有顺序：停止接收新任务 → 给当前任务取消/完成机会 → 隔离旧epoch回调 → drain解码/物化/对象写者 → 关闭DB和对象库 → 销毁QObject。不得为关闭一个未创建服务而创建它。未drain不能报告“安全退出”。

## 13. 兼容导出与原件导出的完整设计

### 13.1 新工程 → 旧`.prism`

1. 锁定目标旧版本能力与冻结修订R；若有无法表达的功能，预检拒绝“完整兼容”并列出具体项。
2. 从权威快照复制全部实例与业务表，不只复制当前驻留画布；把去重对象按旧schema的每实例关系重新内嵌。
3. BLOB流式写入`zeroblob+blobopen`，不经过QImage；页面/附件走后端统一读取器。
4. 验证原件哈希、ID/关系/正文、全局metadata与未知字段范围；专用旧版程序副本实际重开验证，不能仅检查user_version。
5. 在目标同卷临时路径完整写好再发布；失败/取消不破坏既有目标，不重新绑定当前工程到失败目标。

旧格式一实例一原件时，导出体积可能大于去重后的新目录。这是目标格式约束，不允许靠损失数据维持“小”。

### 13.2 原件导出

从冻结SourceRef打开原字节流，写专用目标临时文件，同时计算SHA256；完成后校验长度和身份，再发布文件。批量部分失败要有逐项written/skipped/failed清单，不能只给总体“完成”。

存储层校验失败、缺少codec/字典、外链变动都应失败，不得降级到缩略图、首帧、RGB8或空DOCX。显示用LOD、预览编码与原件导出路径严格分离。

## 14. 分阶段开发与并行边界

本节用于后续分工，没有启动新AI或修改文件owner。每阶段有明确停点，不能以无限审计替代交付。

| 阶段 | 完成内容 | 可并行部分 | 必须等待 |
|---|---|---|---|
| S0 基线与工作负载 | 真实数据分布、引用/未知数据清单、冻结样本和旧版能力 | 只读计量、依赖评审、格式设计 | 不跑并发重型性能 |
| S1 来源/后端契约 | LegacyBackend先实现接口，未来版本拒写 | 旧格式回归与第三方独立小原型 | SourceRef/receipt/版本契约先定 |
| S2 对象库与新格式 | DOS适配、metadata模型、锁/关闭/崩溃协议 | 媒体适配、UI入口可按稳定桩开发 | 同文件唯一写者 |
| S3 离线迁移 | 预检、流复制、检查点、全量校验、发布 | 验证器独立编写，旧版导出器并行 | 读写契约与对象持久化先稳定 |
| S4 查询与工作集 | 下推、dirty覆盖、紧凑ID、几何复用、总预算 | 渲染与查询在接口冻结后并行 | 共享asset_records/浏览器按owner串行 |
| S5 无损导出与便携包 | 原件字节导出、旧格式导出、可选Zstd包 | 独立codec评测 | codec/manifest版本先冻结 |
| S6 独立验收 | 冷热/中断/重开/原件校验/真实十万交互 | 小正确性测试可分进程 | 单重型原生窗口、固定候选 |

推荐6个职责：集成与契约、后端/对象库、迁移/恢复、查询/工作集、媒体/导出、独立验收。不是越多AI越快；同一产品文件只有一个写者，对照实验只能在隔离副本，不能临时覆盖共享树再恢复。

现有性能修补与存储演进可并行的前提是边界不冲突；不能为了做新格式暂停已确定的保存正确性修补，也不能让架构大改覆盖尚未收口的WIP。

## 15. 验收：什么能够独立证明正确

### 15.1 数据与兼容必须全部通过

| 编号 | 验收场景 | 通过依据 |
|---|---|---|
| V01 | 旧schema/现schema旧文件直接打开 | 既有实体、正文、原件一致；无强制转换；源保护符合打开模式 |
| V02 | 只驻留一个画布后保存/转换 | 未加载行、全局元数据、附件不丢 |
| V03 | 旧文件→新目录→兼容旧文件 | 全实体/关系/原件哈希对照，目标旧版真实重开 |
| V04 | 迁移后移走旧源 | 新工程无隐式旧路径依赖 |
| V05 | byte-identical重复＋视觉相同但字节不同 | 前者去重，后者不合并；实例独立 |
| V06 | ICC/EXIF/透明/16位/HDR/动画/视频/GLB/文档附件 | 原件导出完整SHA256相同，不以截图代替 |
| V07 | 未加载正文/空正文/损坏正文 | 完整读出、合法空、明确失败三种结果 |
| V08 | 取消/满盘/权限/源改动/锁冲突 | 原源和既有目标不损坏，失败不报成功 |
| V09 | 每个持久化/发布边界强制进程结束 | 重启只出现完整旧状态或完整新状态；允许孤儿对象不允许悬空引用 |
| V10 | 保存期间新编辑、重复回执、A→B→A | 新编辑保留dirty，旧epoch不覆盖新状态 |
| V11 | 删除/撤销/导出/备份与维护重叠 | pin与租约有效，不误删读者需要的对象 |
| V12 | 未知列/JSON键/表、未来必需能力 | 可保留范围证明；不支持明确阻挡，绝不静默丢弃 |
| V13 | 缓存全删/缓存损坏 | 权威数据正确，目录和预览可重建 |
| V14 | 中文/长路径/同名/跨盘迁移/目录重定位 | 内部引用不依赖旧绝对路径；安全拒绝别名覆盖 |
| V15 | 对象/包截断、改一个字节、缺字典 | 检出损坏或缺依赖，不输出假原件 |

哈希必须覆盖完整原件，样本只证明样本。迁移结果schema/语义清单、独立读取器与原件哈希共同作证，不只依赖迁移器自己返回True。进程崩溃模拟不等于物理断电测试，报告分别标明。

### 15.2 性能不能用一张成绩表笼统通过

规模至少100/1000/10000/100000实例；独立原件与复制实例分开；图片、正文、材质与视频分型。固定参考机器、Windows/Qt/Python、磁盘、DPI、原件分布、空闲空间和并发状态。

分别测旧优化后A、分离式B/C；同样预览和查询，不通过降低画质或忽略原件缩小工作量。真实冷缓存只能在可复核条件下称冷；不知道就标缓存状态未知，不主动清全机缓存影响用户。

必要指标：首可操作、首画布可见、计数确认、查询完成、安装/几何提交、焦点及全视口清晰时间、主线程停顿P95/P99/max、GC及存活对象、实际I/O、常驻与峰值RSS、缓存字节、临时空间、导出/迁移吞吐、压缩/解压CPU。

建议先冻结下列结构门槛，再校准硬件相关时延门槛：

- 改一条标签不读取/重新编码无关原件；日志必须给出原件读写0的可信计量或明确unknown。
- 回到有效热查询不得全量重建重代理；身份/dirty变化则正确失效并报告原因。
- 视口交互不因全库规模产生等比例GUI对象分配；可见/邻域对象和解码缓存有实际预算。
- 十万独立原件下仍具备有界额外迁移内存；不能依赖数据大量重复才能通过。
- 保存和迁移进度有可观测状态；“排队/复制/校验/提交/完成”分开；未知总量不用假百分比。
- 正常热点不持续产生超过预算的单次GUI工作；超出时记录归因，不能扩大timeout当性能修复。

具体毫秒SLO在S0参考机基线与产品体验评审后签字冻结；本设计不编造已经达到的数值。性能改善必须同时满足正确性，不能用“更快”抵消丢字段。

## 16. 每包交付、失败处理与停点

每个开发包交：

1. 包号、实际产品入口、可写文件/唯一owner、依赖契约版本。
2. 改前原字节、改后原字节、完整SHA256与diff；重建件不能冒充事前快照。
3. 修掉的具体旧缺陷、同树隔离before/after对照；没有复现就不写“已解决”。
4. 原始命令、源码摘要、开始/结束、退出码、JUnit/日志、实际I/O和内存口径。
5. 数据校验清单、未支持/未测、残留进程、原件保护与设置隔离记录。
6. 未完成问题、下一具体函数、接口接收者；状态区分取证完成/代码待验/独立验收通过。

第一版目录格式的发布闸门是V01—V15和选定性能工作负载通过，而不是“核心API能读100条”。若对象库适配不满足只读、媒体或恢复契约，停在实验后端，不迁移用户原件。

## 17. 仍需实验决定的事项

1. 当前真实库的独立原件比例、可压缩比例、空闲页与缓存占比：本次未读取用户数据库，不给空间节省百分比。
2. DOS在Prism现有媒体、打包运行环境、并发只读与退出路径的适用性：已读源码/CI，不算集成通过。
3. pack目标大小、单对象阈值、预取并发、总缓存预算：通过随机/顺序读、NTFS文件数和维护峰值决定，不照抄默认4GB。
4. Zstd与zlib/LZMA在真实素材组合的收益：官方文本语料不能代表JPEG/MP4；首版不启用字典训练和自研分块引擎。
5. 旧发布版本逐项能力：必须指定二进制版本/哈希和测试夹具，不能用“所有旧版”作无法验证的承诺。
6. 原生退出故障、材质几何与GC剩余持有图：属于独立修补线，存储演进不自动销号。

本方案的下一具体交付应是S0数据分布与S1兼容后端契约，随后做小规模可恢复迁移原型；不是直接给55GB工程跑转换，更不是立即重写引擎。
