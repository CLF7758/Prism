# 旧模型多材质方案（已由 V2 框架方案替代）

请改读 [V2 框架与开发交接](MODEL_MULTI_MATERIAL_FRAMEWORK_20261027.md)。V2 已搭代码骨架并提供四份独立 AI 任务书。下文仅保留历史，不再作为开发契约。

日期：2026-10-27。范围：用户提出的第四项。目录、拖动整理、Delete、重命名属于另一组已实施的管理功能；本文不把它们当作多材质已完成的证据。

## 1. 用户最终看到什么

模型库中间继续显示“整件模型已经上好材质”的封面。导入时先还原模型已有材质，不先套默认白材质球，不要求用户重新把所有图接一遍。双击仍进入模型大预览。

右侧原来的“贴图槽位”页签改成“材质（N）”，另一个“版本与文件”页签保留。左侧资源树仍然只是模型目录，不把模型内部材质混入文件夹树。

例如一辆车有车漆、轮胎、玻璃、内饰四种材质：

1. 选中车模型，右侧显示四张小材质卡：小球预览、材质名称、使用部件数量、原始／已修改／缺图状态。
2. 默认保留四种原材质的绑定，整车封面显示原来的效果。
3. 点“轮胎”，下面才显示轮胎的底色、法线、粗糙度等贴图及参数。原有贴图槽位控件复用在这里，它们属于当前材质，而不是整个模型。
4. 给轮胎换材质，只改变轮胎。车漆、玻璃、内饰保持原样。
5. 如果确实想整车同一种材质，必须明确点“应用到全部 4 个材质”，不能把它当成默认操作。

材质球只是该材质的小预览，不是另一个需要用户手动创建、手动保存的素材。原模型可能用了平面、毛发、玻璃等材质，标准球预览无法表达时应给出用途标记，最终效果看整件模型。

## 2. “有几个材质”必须数对

必须分别记录材质定义与几何绑定，不能拿网格数量或 F3D actor 数量充当材质数量。

- 一百个网格共用同一个材质：显示 1 个使用中的材质，可查看“100 个部件共用”。
- 一个网格的三个面组分别使用三种材质：显示 3 个材质。
- 两个材质重名：保留为两个独立定义，以原始 ID／索引区分，显示名称允许相同。
- 文件定义 5 个材质但只使用 3 个：标题显示“材质（3）”；“版本与文件”记录“使用中 3，文件定义 5”，不自动删除闲置定义。
- 面组没有绑定材质：列为“未指定材质”并列明受影响部件，不伪造“导入成功并已贴好”。

用户从材质列表选择一个材质，编辑范围就是它。可提供“查看使用部件”，高亮／拾取必须以后端实验证实为前提，不能把高亮功能画出来就宣布支持。

## 3. 材质从哪里贴

第一入口是导入时已有的材质。第二入口是 Prism 现有材质库。第三入口是当前材质内部补贴图。

### 导入已有材质

完整读取原文件的材质定义、参数、贴图引用、UV 通道、纹理变换、Alpha、双面、法线约定和扩展；建立几何面组到材质的对应关系。能表达多少就还原多少，明确列出缺失与不支持。

### 使用 Prism 材质库

在选中的模型材质卡上提供“从材质库替换”。打开现有材质库的选择器，选中一项后把完整材质快照应用到当前模型材质；也支持把材质库卡片拖到指定模型材质卡上。

默认采用**快照**：换完后模型自己的外观独立保存，之后修改材质库源记录不会悄悄改变所有模型。保存来源材质 ID、版本与名称用于追溯；不默认引入跨资产实时联动，也不增加一个让用户困惑的“同步设置”。用户再次主动替换时才更新。

选择器应有预览、应用、取消。点击应用才提交；取消不留外观修改。一次替换是一条可撤销命令。

### 手动补贴图

点当前材质下的已有贴图槽位，使用现有文件选择、附件存储、通道选择、色彩空间与参数控件。仍然可以直接拖贴图到当前槽位；不能把“拖一个颜色图到模型”偷偷解释成替换所有材质。

替换后可“恢复此材质原始状态”，只撤掉这一材质的覆盖。另提供明确的“恢复模型全部原材质”，需显示影响数量。

## 4. FBX、OBJ、GLB、glTF 的导入规则

### glTF／GLB

材质定义以 `materials[]` 的索引为来源身份；几何绑定从 mesh primitive 的 `material` 读取。纹理通过 `textures`、`images`、bufferView 或外部 URI 找到实际内容。记录 samplers、texCoord、KHR_texture_transform 及相关 PBR 扩展；variants 是可选的替代绑定，不重复算成另一模型。

保留 metallic-roughness 通道语义：G 为粗糙度、B 为金属，AO 取 R；颜色／自发光 RGB 与数据贴图的色彩空间不同。不得从文件名猜 ORM 通道。

### OBJ／MTL

从 `mtllib` 找 MTL，从 `newmtl` 找定义，从每个 `usemtl` 的面组建立绑定。`Kd/Ks/Ns/d/Tr/illum`、`map_Kd/map_bump/map_d` 等按原始语义保留。

OBJ/MTL 不是完整的现代 PBR 标准。`map_Ks` 不是通用的粗糙度槽，bump 不必然是切线法线。作者另外提供 Metal/Rough/AO 图片但没有可验证绑定时，列为“附带但未绑定”；可以依据作者明确说明提供建议，但必须把建议与文件中真实绑定分开。

当前水桶与肉钩样本有作者 F: 盘绝对路径。只在本次资产包中找唯一同名文件作为可追溯的路径修复；同名冲突列出候选，不扫描整个电脑随便挑图。原 MTL 不改写，修复映射另存工程。自动补齐依赖不等于自动猜对 PBR 通道。

### FBX

从 Material、Texture、Video、对象连接和几何的材质索引读取定义与绑定；处理独立贴图、嵌入媒体与作者 `.fbm` 目录。一个 Geometry 可绑定多个材质，多个 Model 节点也可能共享材质。

不能只读“模型引用了哪些图片”就宣布掌握了多材质关系。还要证明图片连到哪个材质属性、材质分配到哪些面／部件，以及渲染器加载后是否保持该关系。

FBX 的 Phong／Lambert 或 DCC 专有节点不能强称为完整 PBR。支持项做有依据的映射，其余保留源信息并显示具体限制。缺贴图时报告缺的是哪个材质、哪个槽和哪个引用；不能让所有材质一起变成无法定位的灰模。

### SSS 与置换

仅在源格式实际保留了定义，且后端实测支持时启用对应编辑。20 个下载样本的柠檬、洋葱仅在作者 .blend 中有真实 SSS，作者 glTF 未保留；不能用这两个目标 glTF 验收 SSS。

## 5. 架构边界与保存内容

保持原件、解析结果、外观覆盖、派生缓存四层分离。

1. **原件层**：现有 ModelResourceStore 管模型、贴图、MTL、BIN 等不可变原件，继续逐文件 SHA-256。解析、重命名和材质修改不得写回原文件。
2. **材质清单层**：新增版本化 `material_manifest`，按 source_revision 保存材质定义、实际绑定、解析证据和未支持属性。解析在后台／隔离进程执行，不在 GUI 扫大模型。
3. **外观层**：现有 ModelAppearance 扩展为按 material_id 保存稀疏覆盖；没有覆盖就使用原材质。保留旧的单一全局覆盖字段，作为明确的“旧版模型级覆盖”读入，不能在升级时擅自复制到每个材质。
4. **派生层**：整模型封面、材质球小预览和可能的预览工作文件可重建。缓存键包含源版本、材质清单版本、外观版本、相机、后端版本；不会反向成为原件。

材质清单最少字段：schema_version、source_revision、parser/version、materials、assignments、unresolved_references、unsupported_features。每项材质包含稳定 material_id、source_id／index、name、workflow、参数、纹理引用、来源证据。每项 assignment 指向稳定 mesh/primitive/面组 ID 与 material_id。

material_id 不由显示名称产生；重命名不能改变绑定。材质库快照不保存对全局活动材质对象的可变引用。模型重新导入时，用来源身份做版本迁移；无法确认对应关系的旧覆盖进入“待重新匹配”，不静默套给另一材质。

写入命令携带 project_session、open_epoch、model_id、source_revision、appearance_revision、material_id。保存期间的新编辑另记新版本，旧解析／封面回调不能覆盖新状态。未知字段在保存重开时保留。

## 6. 当前后端的事实，不能跳过

本地 `prism/model_library/f3d_parameters.py` 目前把外观映射到全局 `model.color.texture`、`model.normal.texture`、`model.material.texture` 等选项；无覆盖时保留导入的多材质，但这不等于已有“只改第 2 个材质”的端口。

本地安装的 F3D 4.0.0 Python Scene 公开接口可查场景层级、设置节点可见性、取场景统计；本轮接口枚举没有发现可直接按材质 ID 替换材质的公开方法。不能把 actor 数当材质数，也不能把全局覆盖包装成一个看起来有列表的假多材质界面。

现有材质球渲染使用本地 Babylon PBR 查看器（`prism/widgets/material_render.py`），可复用材质参数与球预览，但它目前不是已验收的 FBX/OBJ 整模型多材质后端。

因此先做隔离实验，再定后端接法：

- A：继续 F3D 原始格式读取，验证可维护的原生扩展是否能暴露稳定的材质／几何绑定以及局部材质更新。不能依赖 Python 私有指针硬改场景。
- B：复用现有 Babylon 材质能力，验证 glTF/GLB 原始场景的逐材质编辑。FBX/OBJ 若需工作文件转换，只能生成预览派生文件，并验证几何、UV、材质分组、贴图和单位是否保真；失败时不可悄悄切过去。
- C：若两者都不能满足，保留原始材质查看与清单，明确局部编辑未接入；另评估最小渲染适配层，不为了一个材质列表重写整个应用。

现阶段不预设“换 C++”或“全部转 GLB”就是答案，也不在这个管理功能改动中偷偷换后端。

## 7. 六步实施与交付门

### 第一步：最小实验，决定是否能做局部编辑

用一个三材质、至少两个部件共享材质的模型：只替换第 2 个材质，记录前后绑定、原始参数及渲染。GLB/glTF 先做确定性基准；再各用一个真实 FBX、OBJ 做同一实验。

通过：选中部位改变，其他材质参数及绑定完全不变，原件哈希不变；预览能取消，失败不崩主进程。未通过不扩大 UI 开发、不宣称支持。

### 第二步：导入与清单

实现版本化解析、依赖定位、材质计数和 assignment；独立期望集来自原始 JSON、MTL/FBX 连接关系或 DCC 检查，不由实现代码自己生成正确答案。

通过：重名材质、共享材质、一个网格多面组、无材质、缺图、外部 BIN、内嵌图等案例均能解释。十万模型库只加载卡片摘要；只给选中模型加载清单，不实例化十万个材质球。

### 第三步：右侧材质列表

把平铺全模型贴图页改为材质列表＋当前材质参数。材质多时虚拟化／懒加载小球；先显示名称和状态，再补预览。复用现有 MaterialSlot 控件，不复制一套参数体系。

通过：选择、切模型、切工程不会把上一个模型的材质写到下一个；计数按真实定义与使用关系，缺图定位明确。

### 第四步：局部覆盖与材质库替换

实现当前材质的贴图编辑、参数修改、快照替换、恢复原始，以及明确的批量操作。一个操作一次提交，可撤销；连续滑块拖动合并为一次编辑。

通过：只改指定 material_id，旧全局覆盖能区分，依赖图完整；源材质库更新不自动污染已应用模型。

### 第五步：持久化与失败恢复

验证完整保存、局部保存、保存期间新编辑、重新打开、工程搬迁、解析取消、辅助进程崩溃、磁盘写入失败、缺图恢复与未知字段。

通过：已确认提交的编辑可恢复，未提交编辑不伪装成功；新编辑不被旧回调覆盖；原件导出仍逐字节一致。

### 第六步：真实任务验收

用本地 20 个资产覆盖实际工作流：导入 → 查看原材质 → 选一个材质 → 从现有库替换 → 修改贴图 → 保存重开 → 单个／批量导出原件。另补明确的多材质 FBX/OBJ 资产及三材质独立对照模型，不能拿 20 个样本数量代替多材质覆盖。

分别记录材质定义恢复、局部编辑、透明、自发光、SSS、置换、法线、纯线框的通过与未测。保存 P50/P95/P99、最长停顿与内存／显存峰值时必须附机器和样本条件；本方案没有捏造性能阈值或实测数字。

## 8. 可并行与不可并行

清单格式冻结后，格式解析、材质列表 UI、独立期望集可以分开进行；后端实验可同时进行，但只有明确端口后才能接局部编辑。保存适配必须跟随清单与覆盖格式冻结，不能让多条工作线同时改 ModelAppearance 或最终提交路径。

当前先不实现：跨模型共享实时材质、节点编辑器、模型格式转存导出、自动猜通道、自动改法线、自动补 SSS、全库常驻材质预览。现有“导出原件”仍然只导入时的原模型和原始依赖，不承诺把 Prism 外观修改烘焙进 FBX/OBJ/GLB。
