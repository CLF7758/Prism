# Shared material workflow: current implementation and evidence

## Scope
The current change unifies preview throttling/intent replacement and original-image decode validation. It does not unify the renderers or project data structures. The work is not a claim that all six layers are complete.

## Before / after operation chain
Both libraries use MaterialSlot. Previously the model editor sent every slider signal directly to a backend preview, whereas the material library used a timer. The model editor also previewed only the last incremental option patch, even though its final commit contained the full gesture.

Now PreviewUpdates owns the same latest-intent, non-restarting deadline and cancel/flush policy for both libraries. The material library keeps its existing timer-facing entry point and existing single-in-flight texture preparation/cache. The model panel queues at most one unsubmitted slot intent (33ms ticks), invalidates old result identity immediately, flushes the final intent at gesture end, then submits the one durable gesture command independently. The editor sends the accumulated gesture patch to both preview and commit. Explicit discard/target change cancels queued intent. New previews use supersede if available; older ports lacking supersede let old work finish with its result rejected, instead of invoking a cancel operation that might restore an obsolete frame. Actual explicit cancel retains existing cancellation semantics.

Shared open_decoded_texture fully decodes pixels before either library accepts a texture binding. Caller closes the PIL image. Original bytes are kept; no resampling/encoding is performed for storage. Material metadata analysis remains with prepare_texture, while backend ORM/alpha composition remains distinct.

## Durable material undo/redo implementation
- History is persisted in multimaterial.history in the SAME resource/record transaction and uses row deltas keyed by working_id/binding_id plus changed envelope fields, not complete model snapshots for each step. Input state/history are not mutated. Up to 100 undo steps retained. Unknown state fields preserved; removed rows retain their original positions for restoration.
- UNDO/REDO are explicit material commands using normal idempotent receipts, version checks, resource registration and commit publication. The state revision advances; replaying the same request cannot undo twice. A new editing branch clears redo. Empty/conflicting history is rejected before any data write. History cannot be applied across source/catalog revision; a normal edit of a changed source explicitly starts a fresh history scope.
- Model panel Ctrl+Z finishes the active gesture then submits UNDO; Ctrl+Y/Ctrl+Shift+Z submit REDO. Text controls retain native text undo. Existing observer signal retained for compatibility, but the panel now submits production commands rather than relying on an unconnected signal. Unrelated canvas undo is not called.
- Managed resource registry and snapshots remain roots throughout undo/redo: no original bytes are deleted by history operations or by trimming the undo list. This favors safety; resource compaction/GC is not newly implemented and storage growth must not be claimed bounded by the 100-command limit.
- artifacts/material-history-first-20261029.txt: 22 passed. artifacts/material-history-regression-20261029.txt: 43 passed. artifacts/material-history-final-20261029.txt: 70 passed. artifacts/material-history-ui-final-20261029.txt: 20 passed. Overlapping results are not a unique test total.

## Six-layer semantics follow-up
1. Controls: MaterialSlot owns normal vector channel availability for BOTH adapters; removed duplicated model-editor channel disabling. Existing clear/add/drop/reuse/enable/amount controls retained. Legacy loaded bindings are not silently rewritten.
2. Rules: validate_texture_channel and texture_color_space are authoritative shared policies. Material service and model command validate new bindings before mutation/I/O: known slot, known channel, normal RGB. Normal single-channel edits now fail atomically at the material-service boundary instead of being saved then failing render. Model channel-change without an existing texture now fails instead of creating a silent no-op commit. Clearing is still unbinding, not deleting originals. Historical source-role data is retained separately.
3. Sessions: shared preview intent/gesture/receipt/history work described above. New integration regression found actual material note loss on navigation, not just a timing test issue: DeferredLibrary did not forward the first _preserve_editor_on_show flag, so temporary re-show reset the editor before flush. Explicit flag forwarding works before/after lazy construction; pending notes survive asynchronous page navigation. Original note assertion retained.
4. Images: shared decoded-original content cache and transform helper; per-backend final ORM/alpha preparation retained. No claim that all derived-image caches are unified.
5. Scheduling: shared PreviewUpdates latest-intent tick and flush/cancel semantics; backend execution queues remain different by design, native scene still single owner. Durable edits never enter the replaceable preview queue.
6. Storage: shared parameter/binding validation and transactional resource/history principles; actual material/model record structures remain distinct. No forced database migration.
