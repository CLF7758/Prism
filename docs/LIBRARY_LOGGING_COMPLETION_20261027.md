# 模型库与材质库日志补齐记录

日期：2026-10-27。本文记录实际改动、证据和边界，不承诺任何故障都能完整留痕。

## 现在交付的能力

仍使用 Prism 原有 `performance_trace`、模型事件和诊断 ZIP。新增 `library_observability.py` 是有界的记录适配器，不创建另一个文件日志系统、线程或用户设置。

| 保存及重开 | 已序列化元数据行摘要、准备写入与读回校验；保存事务及界面确认的既有结果分别保留 | 隔离工程真实 SQLite 写入重开摘要一致 |

### 两个实际发现的重要故障

1. **写入线程会静默死亡。** 真实工程重放时，其他日志配置关闭了 `RotatingFileHandler.stream`，原实现访问 `None.write`，写入线程崩溃。现在完整写入和轮转使用 handler 锁，流被关闭时重新打开；无法恢复时明确报告错误和未写队列数量。原始失败证据保留在早期重放日志中，最后一次运行已生成完整诊断包。
2. **记录与业务确认混淆。** 原来部分配置、原生返回、封面及保存边界不能串起来。现在配置记录明确是否只在场景内存；准备写入摘要明确不是事务提交证明；出帧、截图、安装及保存确认保留不同事件。

## 诊断包和使用方法

重启 Prism 后，在「帮助 → 日志和诊断（Logs and Diagnostics）」里复现问题、点击「标记刚才的问题」、再「导出诊断包」。

诊断 ZIP 新增 `library-evidence.json`，包含：

- 模型、材质、纹理及工程边界的累计观察计数；
- 最近 128 条有界证据、至多 64 个在途调用及年龄；
- 至多 96 类阶段、每类最近 128 次耗时的 P50/P95/P99/最大值；
- 记录失败计数、原有日志队列/丢失/写入恢复健康信息；
- 明确列出的范围与未测项。

完整时间线仍在原有 `Prism-operations-*.jsonl`。`library_event/1` 表示新增适配事件的语义版本；原有事件继续兼容。

### 隐私与体积

新适配层只接收字段白名单；不记录原件、贴图 Base64、备注正文、文件选择路径或局部变量。错误位置只保留代码文件名、行号、函数名和摘要，路径及敏感字段经过遮盖。

相同拒收原因的连续过期回调每秒合并，累计计数和合并数量仍保留；2,000 次过期风暴测试没有生成 2,000 条日志。错误事件不走这一合并规则。原有有界队列、轮转和丢失报告保留。

## 保存与重开摘要究竟证明什么

对正在读写的**元数据**做摘要，不新增数据库查询，不读取模型/图片 BLOB。摘要包含 SQL 主键和已序列化载荷，排序后合并，行顺序不影响比较。全量保存的 `write_prepared` 与重开的 `read_validated` 可以核对序列化元数据是否相同。

它不证明原件附件内容正确、不证明截图正确，也不能代替保存事务结果。附件原件哈希及像素检查沿用其他验收。

局部保存记录只涉及修改行，明确标为 `changed_rows_only; excludes deletions`，不能拿它和全工程摘要直接比较。GUI 上的工程边界只读已驻留计数/修订，不扫描延迟加载数据或把驻留计数叫全工程计数。

## 明确边界

- 断电、强制结束进程、磁盘完全不可写时，最后若干条可能无法落盘；有界队列和轮转也会丢失旧证据，查看 incomplete、丢失和保留范围。
- GPU 字节标为 `unmeasured`，不是 0。进程资源为采样值，不宣称瞬时峰值；原生 Render 耗时包含驱动等待，不叫纯 GPU 时间。
- 部分耗时是父子包含关系，例如属性准备包含解码，不可相加当总时间；精确磁盘设备 I/O、显存及 CPU/GPU 分摊仍需外部跟踪。
- 十万真实资产、长期编辑、极端多材质的日志开销、轮转后的长期问题复盘仍未独立验收。
- 诊断增强能说明观察到的失败和停止位置，不是对所有可能问题的自动识别或修复。
