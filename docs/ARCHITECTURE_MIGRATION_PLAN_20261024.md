# Prism 整体架构迁移方案

> 2026-10-24 更新：本文件保留为第一版历史提案。整体目标架构、迁移依赖和实施裁决以同目录 `ARCHITECTURE_TARGET_V2_20261024.md` 为准；本文件中的逻辑职责名称不意味着需要再创建一套同类服务。

日期：2026-10-24。状态：设计提案，未实施、未完成大工程性能验收。

## 1. 结论和范围

当前没有证据表明 Python 已到性能上限。已确认的结构问题包括：交互路径全量遍历、同步搜索和布局、分页接口可能阻塞调用者、跨界面广播带来重复计算、界面与存储存在直接依赖。这些问题应先处理，否则换 C++ 仍保留错误的工作量和等待链。

保留 Python + Qt、SQLite 工程格式、现有图像解码与预览、Babylon 和文档/脑图编辑器。Qt、SQLite、NumPy、PyAV 等依赖本身已有原生实现；不另写一套解码器或渲染引擎。迁移采用一个进程中的清晰模块边界，非微服务化。

本方案与 10 月 21 日交接书并存；10 月 23 日已修复功能以当前源码为准。历史报告不能直接当成当前故障清单。禁止为完成方案重做已有同类服务或撤回近期安全修复。

本轮检查：201 个 Python 文件（排除 vendor）；view.py 3786 行、items.py 2761 行、media_library.py 1987 行。架构测试 31 passed / 1 failed，失败为 document_panel 和 mindmap_panel 直接导入存储加载函数。行数是维护风险信号，不是运行耗时证明。

## 2. 必须保持的数据不变量

- 原始附件字节与可重建预览分离；缓存清除不能损坏原始数据。
- 未加载的数据不是空数据；保存不能把未加载字段或附件写空。
- 修改、删除和撤销使用稳定资源 ID；跨页移动不改变资源身份。
- 只读目录索引可重建，工程数据库是持久化事实来源。
- 当前会话的未保存修改通过统一覆盖层参与查询；旧后台结果不得覆盖新修改。
- 保存、另存为、失败回滚、关闭重开必须保留用户数据。
- 模糊占位、旧帧和最终清晰画面分开计量，不用降低画质冒充提速。
- 用户原工程不作为写入试验对象；所有写入验证使用独立副本。

## 3. 目标依赖方向

界面/输入 → 应用用例 → 领域数据与查询接口 ← 存储实现。
应用用例 → 任务调度 → 后台计算；结果通过 GUI 适配器安装。
渲染仅消费可见数据、布局与预览，不承担全库业务查询。

建议逻辑职责如下。先建立接口和正式接线，后移动文件；表中名称表示职责，不要求立即创建同名类。

| 职责 | 负责 | 复用的现有实现 |
|---|---|---|
| ProjectSession | 工程身份、生命周期、修订号、打开/关闭协调 | project_open_scope、opening_lifecycle、partial_project |
| AssetRepository | 元数据/分页/附件访问和事务边界 | fileio/sql、source_store、attachments_store |
| AssetQueryService | 单一查询入口，索引加未保存覆盖层 | project_catalog、project_catalog_index、search_candidates |
| AssetChangeSet | 稳定 ID 的增删改、受影响字段和修订号 | commands、undo、item_metadata、partial_domains |
| PageController | 切页提交、取消旧任务、页内容驻留与释放 | window_workspace、paged_canvas_loader、partial_residency |
| TaskCoordinator | 优先级、取消、背压和过期结果过滤 | scene_loading、image_decode、paged_open_preparation 的已有调度 |
| ViewportRenderer | 可见区域查询、LOD、瓦片与局部失效 | viewport_items、canvas_tiles、canvas_composites、lod |
| PreviewService | 解码、派生图和预览请求去重 | image_decode、image_pyramid、thumbnail_cache、video_thumbnails |
| ResourceAccounting | 可重建 CPU 缓存预算及独立资源观测 | resource_budget；GPU/子进程/撤销历史另列 |
| Document/MindMap Adapter | 编辑器通信、提交和延迟内容加载适配 | document_panel、mindmap_panel 与现有编辑器 |

不要把所有职责集中成一个万能管理器。不同任务可以共享调度协议，不共享不适用的线程执行器。

## 4. 数据模型：一份事实来源，多个受控投影

工程数据库 → 只读索引 → 查询结果分页 → 可见项投影。
未保存变更 → 统一覆盖层 → 查询/计数/保存。

1. 数据记录不依赖 QWidget/QGraphicsItem。持久化身份以 asset_id/page_id 为准。
2. Qt 图元是显示与交互适配器，不充当全库数据库。
3. 查询返回 ID、必要元数据和游标，不默认创建全部卡片或附带原文件字节。
4. 明确已加载页、全工程、筛选结果三种范围；不能用当前场景数量代替全工程数量。
5. 兼容旧接口时在边界转换，不能长期维护第三份同义全量记录集合。
6. 目录聚合与未保存覆盖层在查询服务中统一合并，界面不自行再合并一遍。
7. 缓存键包含工程身份、必要修订号、查询/页面/LOD 参数；细分元数据、几何、源文件和预览修订，避免一次改名失效全部图像。
8. 外部文件变化在必要的数据访问边界验证；把验证移出滚轮回调，不取消有效性验证。

## 5. 执行模型：GUI 不等后台

- GUI：输入、轻量状态切换、局部绘制、分批安装 Qt 对象。
- 后台线程：文件 I/O、SQLite 查询、已有能释放 GIL 的原生解码。
- Python CPU 密集任务：先改善算法、批量化；再比较进程或原生扩展。大图/全库对象不要反复通过进程复制。
- GPU/WebEngine：保留各自线程与生命周期；不能把有线程亲和性的对象随意放进线程池。

统一任务信封：project_id、session_generation、page_id、query_generation、相关 revision、priority、cancel_token。GUI 安装前核对身份和修订号。

优先级：当前输入反馈 > 当前视口清晰图 > 当前页元数据 > 相邻视口 > 全局索引/预取。每类队列有长度/字节上限，同一资源同一层级合并请求；切页/缩放撤销失去价值的任务。取消需在计算和 I/O 批次边界协作检查，不能只取消结果展示。

GUI 取页接口返回 ready/pending/error，不得等待 Condition 或同步读取缺页。异步请求页与仅后台可用的阻塞读接口分开命名。后台结果通过信号批量进入 GUI，安装采用时间预算并统计单个不可拆任务超支。

## 6. 渲染和布局

1. 绘制、命中、框选共用空间索引与几何语义。交互成本应主要随可见/实际命中数增长。
2. 缩小后使用分块合成和层级预览，不能每次重新创建/排序全库卡片。
3. 正常分组路径与合成失效后的回退路径都需有工作量上限；不能只测缓存已就绪状态。
4. 布局计算输出紧凑坐标数组和边界，不输出 GUI 对象；后台计算，GUI 分批安装。
5. 布局缓存命中仍要避免全量恢复；未变化的坐标、索引和合成缓存保持有效。
6. 局部修改只失效相关空间块；全局重排是明确的重操作，有进度和取消。
7. 选择状态独立维护 ID 集合；选一张图不重新排序整个工程。
8. 解码完成批量通知受影响区域；变更事件表达实际范围，不默认广播全场景失效。

## 7. 查询、统计与变更事件

查询、计数、标签树和搜索通过同一查询服务获得一致快照。搜索需可取消、分页、限制首批结果，后台排序/聚合；界面不在每次按键后同步合并所有结果。

变更事件携带项目/修订/受影响 ID/变化字段。改评分仅影响相关过滤和卡片，不失效几何和原图；移动坐标仅影响旧新区域；改标签更新相关集合和统计；原文件变化才更新派生图。

计数优先在变更提交时增量更新，事务内发布一致版本；复杂情况退回后台重算。保留可靠的重建校验入口，不因增量统计提速而默默容忍漂移。

先复用已有 count_snapshot 发布机制，补齐仍重复获取的调用。信号合并以一个提交周期为单位，不能长期屏蔽通知或让其他面板看到不同版本。

## 8. 保存与编辑器边界

文档/脑图界面通过应用加载接口读取延迟内容，不直接导入 SQL 模块。接口仍可调用现有 load_deferred_board_extras，不重写存储。

应用层负责编辑器提交屏障、脏记录快照、附件引用校验和保存事务；界面只展示进度/错误。切页前完成必要提交，后台保存使用固定修订快照，保存完成仅清理对应修订的脏标记。

初期不同时大改文件格式、数据库迁移和渲染。先保留现有安全保存实现，经独立数据回归后再讨论增量持久化。缓存索引完成不等于保存完成。

## 9. C++ 决策和接入边界

目前结论：没有到必须整体转 C++ 的阶段。先完成有界交互和异步边界；可以同步准备小型原生内核试验，但不得直接改写整个 UI/数据库/解码器。

候选顺序：

| 候选 | 前提与边界 | 不应做的事 |
|---|---|---|
| 批量几何/可见候选筛选 | 剖析证明 Python 几何循环占显著 CPU；输入坐标数组，输出 ID/位掩码 | 每张卡一次跨语言调用；更改精确命中语义 |
| 布局计算 | 优化工作量后，pack_sizes 等仍占主要 CPU | 把 GUI 卡片创建一起塞入 C++ |
| 批量元数据变换 | SQL/索引推下去后仍存在纯 Python 重循环 | 为单次查询复制整个数据库到 C++ |
| 预览像素处理 | 已有 NumPy/Qt/PyAV 路径确实不足 | 另写视频解码器或 PBR 内核 |

建议扩展职责独立于 Qt 对象，通过薄绑定传递连续数组、ID 和数值；评估 pybind11 等绑定方案，选定前另做官方文档与打包兼容性核实。计算期间在可行处释放 GIL；GUI 对象只能由 GUI 线程创建/修改。共享缓冲区明确所有权、生命周期、只读约束和取消行为。

原生实现必须有 Python 等价路径/切换开关、精确性对照、异常处理、Windows x64/Python 3.12 构建和安装包验证。统计数组转换、数据复制、绑定开销、峰值内存，而非只展示 C++ 函数耗时。

采用门槛（建议标准，不是已测结果）：改算法与工作量后，某纯 Python 内核仍占目标交互 CPU 时间 ≥30%，且原生端到端试验收益 ≥20%，才正式引入。若主要时间在 I/O 等待、Qt 对象安装、GPU 或信号队列，转 C++ 不作为首选。

Amdahl 示例：热点占 20%，即使该热点无限快，总体也只能约 1.25 倍；热点占 70%、内核快 10 倍，总体约 2.70 倍。不承诺整项目十倍提速。

## 10. 分阶段迁移与每包交付

| 阶段 | 具体交付 | 放行标准 | 回退点 |
|---|---|---|---|
| P0 当前基线 | 固定源码快照、真实副本、启动入口、冷热和采样条件；短剖析归因 | 同动作可重现，记录 GUI、CPU、I/O、内存和画质 | 原源码快照 |
| P1 会话与查询边界 | 统一身份/修订信封；文档脑图加载走服务；明确 ready/pending 查询接口 | 架构测试通过；旧结果不跨项目安装；无未加载数据丢失 | 原适配入口 |
| P2 有界绘制与布局 | 修可见候选回退、全库同步布局、缓存命中重装；后台计算与分批安装 | 可见数固定时扩大全库不会等比例增加绘制工作 | 旧渲染/布局策略开关 |
| P3 搜索与统计 | 后台分页搜索、变更集、单快照计数、合并通知 | 最新查询获胜；统计与重建一致；无 GUI 缺页等待 | 旧查询入口，保留相同语义 |
| P4 生命周期和资源 | 页驻留/释放、解码去重和优先级、CPU/GPU/子进程分账 | 反复切页后资源趋稳；当前视口不被预取挤占 | 原缓存/调度策略 |
| P5 原生内核试验 | 仅选择剖析证实的一个 CPU 热点，原生/原实现 A/B | 准确性一致、端到端达收益门槛、打包可用 | 禁用扩展即恢复 |
| P6 物理模块整理 | 按已稳定的职责拆 view/items/media_library，移除旧入口和重复状态 | 正式入口都走新边界，相关功能无回退 | 分批提交/文件备份 |
| P7 发布验收 | 真实工程重复操作、保存重开、安装包和日志证据 | 性能目标与数据正确性同时通过 | 上一可用安装包及数据备份 |

每包只做一个完整垂直切片：改服务但界面仍走旧路径不算完成。每包必须交付：改动文件、正式调用链、前后工作量、同条件耗时、正确性结果、未覆盖项、回退步骤。基线之后不反复跑无关全量测试，按变更验证，阶段收口再做集成回归。

## 11. 性能验收矩阵

数据集：100、1千、1万、10万素材；图片/视频/文档/脑图/材质混合；单页密集与多页分散；真实大工程专用副本。记录硬件、分辨率、DPI、磁盘、后台负载、源码版本和采样开关。

场景：冷/热打开、切页、连续缩放、平移、全览、局部选择/移动、搜索输入、改标签、保存另存、取消任务、关闭重开、缓存逐出后恢复、连续重复切换。

指标：输入到首次反馈、GUI 事件/安装片段耗时、长停顿次数和最坏值、目标内容首帧、焦点/视口清晰完成、候选/绘制/解码/查询次数、主进程与子进程 RSS、CPU/GPU/磁盘、后台队列长度。

建议目标（设计目标，未验证）：

- 常规拖动缩放 GUI 工作片段 p95 ≤16ms、p99 ≤33ms；如硬件/画质不允许，明确降为稳定 30FPS 档而非隐式降低内容质量。
- 常规交互不出现 >100ms 单次同步工作；首次重操作单独报告，不藏进平均值。
- 当前页首批可操作 ≤1s 热态 / ≤3s 冷态；大附件最终清晰单独记录。
- 搜索首批反馈 ≤100ms、首批结果 ≤300ms（已有索引的热态）；冷索引显示准备状态，禁止假装结果为空。
- 固定可见数量时，总数据从1万到10万，绘制候选/安装数量应保持接近；任何全量路径须单列解释。
- 重复切页30轮后可重建缓存符合预算、任务数回落，RSS不持续单调增长；不要求 RSS 精确回到初始值。
- 保存前后记录数、附件摘要、页面结构、标签和撤销语义一致；失败/取消不破坏原件。

先做冒烟并判断实测成本，再安排10万级测试；不能一开始长时间占用用户工程。样本少只列样本值，不包装成稳定分位数。Qt paint 完成不等于屏幕实际呈现，现有 display_confirmed 边界继续保留。

## 12. 首个实施包

推荐从 P0 加 P2 的素材画布垂直切片开始：定位 arrange 与 visible_cards 的实际调用频率和成本 → 修有界候选与缓存命中路径 → 分离布局计算与安装 → 以固定视口、逐级扩大全库做前后对照。

同时只补该切片依赖的会话/取消协议，不先花大量时间移动所有目录。确认这包改善真实操作后，再推进搜索/统计与跨模块边界。P5 是否实施由剖析结果决定，P6 不成为性能优化的前置大工程。
